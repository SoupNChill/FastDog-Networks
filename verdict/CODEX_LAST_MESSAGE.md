## Eight-area negative findings and boundaries

1. **Auth/key handling:** Looked for plaintext comparison and key-rotation bypass — not vulnerable: API and read-only panel keys share SHA-256 hashes, fixed-size `timingSafeEqual`, iteration over active records, and persisted revocation. `advsec auth: rotation, revoked keys, hashed storage and empty config` locks this down. Missing/empty credentials fail closed on protected routes. Creation intentionally returns the new credential once (CLI stdout/API response); ordinary logs and list output do not contain plaintext. File mode is a code/deployment expectation, not asserted as a platform-dependent unit test. Parent directories must remain operator-owned, mode 0700; no protection is claimed against an attacker controlling parent directories. Explicit bootstrap opt-in is still an administrative exception.
2. **Forward auth/headers:** Looked for leftmost XFF, X-Real-IP and RFC Forwarded precedence bypass — not vulnerable for remote peers; local proxy uses rightmost valid XFF, with X-Real-IP fallback. `Forwarded` has no influence. Forwarded host trust was fixed. Caddy must overwrite host/IP/original URI/method; all local processes share that trust boundary. Client UA/hints are risk signals, never clearance credentials: a spoofed bot UA still challenges and sets no cookie in the new demo/forwarding tests. Existing `redirect destinations are local paths only`, `safeNext rejects open redirects`, and browser redirect tests lock path/header redirect injection. Arbitrary ordinary-browser spoofing can still lower heuristic risk; this is not proof of identity and does not mint clearance.
3. **Demo gating:** Looked for query, header and body force escalation — production variants are now ignored or rejected; allowed demo behavior has positive regression coverage. Demo parameters cannot change host config or PoW difficulty. A malicious local proxy can lie about the host; that is the documented trusted boundary, not an untrusted-header guarantee.
4. **PoW/cookies:** Looked for wrong-secret, truncated-MAC, extra-segment and algorithm confusion — not vulnerable: fixed HMAC-SHA256 and timing-safe comparison, with no algorithm selector. New tests cover host/IP-prefix/expiry replay, precomputed unknown IDs, consumed proofs and invalid difficulty. Existing tests cover unsolved proofs, expiry, altered signed hints, UA binding and capacity. Pending random 192-bit IDs bind the proof to server-held identity; consumption is single-use. Clearance reuse within the same IPv4 /24 or IPv6 /64 and TTL is intentional. Direct challenges still have the documented 16-bit floor; score hints may raise difficulty. The production arithmetic bypass was fixed; the demo-only accessible fallback remains intentionally weaker.
5. **CLI/config/reload:** Looked for shell injection and hostname-based filesystem traversal — host CLI uses encoded URL segments and no shell; host configs are one operator-selected file, not files named after user input. The new CLI test actually sends injection and denylist variants to an ephemeral fixture API. Generator paths containing shell syntax remain literal. Config symlink/size risks and unsafe automatic apply were fixed. Parent-directory TOCTOU is excluded by the operator-owned-directory requirement. Automatic reload is deliberately no longer supported: review snippets and use the operator workflow. No Caddy binary or reload path was executed in tests.
6. **Panel:** Looked for unauthenticated decisions/keys and session CSRF — operational routes require bearer auth; `/metrics` was the aggregate-data exception and is fixed. There is no separate panel-key verifier or panel session cookie in this directory. Read-only keys cannot mutate or call decide; a cookie containing a key does not authenticate. Clearance cookies are host-only, Secure, HttpOnly, SameSite=Lax, and do not authorize panel/API operations. The server defaults to loopback; existing `server defaults to loopback and accepts explicit VERDICT_BIND` locks that down. Reviewed service/proxy examples do not advertise a public panel bind. Explicit operator bind overrides remain possible.
7. **Guardrails:** Looked for case, trailing dot, port, whitespace, NUL, encoding, punycode and shadow/enforce confusion. Case/dot/port variants canonicalize; malformed/encoded/Unicode inputs cannot become config entries. Valid punycode A-labels denote different DNS names from the ASCII denylist. API, real CLI, store and runtime regression coverage prevent enforce configuration or enforcement on canonical guardrail hosts. Shadow scoring continues to record hypothetical actions only; it does not send an enforcement response.
8. **Decide DoS:** Looked for unbounded JSON/header inputs, nested-object recursion, pathological regex and blocking DNS. Body size was already bounded; new depth/value/header checks reject early. Scoring regexes have no identified nested ambiguous quantifiers and now operate on bounded input. ASN lookup is in-memory binary search; the small static hosting set now loads before requests. Default edge auth performs no DNS; optional good-bot DNS is asynchronous with a deadline and capped cache (existing hermetic resolver tests). In-flight connections still require deployment-level connection limits; this is not a volumetric-DDoS guarantee. Map cleanup remains linear in a hard-capped map, and queued log saturation deliberately drops new log records while metrics continue. Tests exercised only small fixture requests and pure functions, not live load.

## High/critical exposure on pre-PR master

**No critical finding established.** High-severity code findings present on the reviewed master are: production arithmetic clearance bypass; demo forcing without a host gate; missing runtime guardrail/off/shadow protection; and empty-store bootstrap through a loopback proxy. The latter three require the deployment conditions described above. These are code-level exposure statements, **not claims that the current live configuration is exploitable**. No live configuration, production service or secret was inspected. The arithmetic path is exposed whenever production challenge routes and a clearance secret are configured as in the reviewed implementation.
